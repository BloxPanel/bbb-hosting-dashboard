# BBB Error Protocol v2.0

The backend error registry is defined in [`src/errors.ts`](../src/errors.ts).
The `BBB_ERROR_REGISTRY` export is the authoritative set of current public and
legacy error identifiers, including each identifier's stable numeric code,
category, severity, and safe message. Categories and existing numeric codes
are stable; do not repurpose them.

## API failure response

HTTP status and existing response fields keep their current meanings. API JSON
failures additionally include:

```json
{
  "success": false,
  "error": "INVITATION_ALREADY_REDEEMED",
  "code": 6005,
  "message": "This invitation has already been used.",
  "reference": "BBB-AUTH-8F2A91C74D60",
  "incidentRecorded": true
}
```

`reference` is generated by the Worker from six cryptographically random bytes
(the first 12 uppercase hexadecimal characters from its cryptographic UUID
generator). D1 enforces uniqueness; a collision is retried up to four times.
Responses are finalized only after the incident insert attempt, so the exact
response reference is the one stored in D1. `incidentRecorded: true` means it
was persisted. When it is `false`, the
reference is not guaranteed to be searchable in D1; a safe structured Worker
log is the fallback. The dashboard must show or copy the backend reference and
must not generate a second reference for the same failure.

All existing HTTP statuses, numeric BBB codes, identifiers, and customer
messages remain compatible. The error `message` remains safe for customers;
the internal diagnostic reason is separately allowlisted and never contains
exception text.

## Incident storage and logging

Additive migration: [`migrations/0009_incident_registry.sql`](../migrations/0009_incident_registry.sql).
`incident_records` stores the unique reference, category, numeric code,
identifier, HTTP status, normalized operation, service/component, UTC ISO-8601
timestamp, severity, expected/unexpected classification, safe diagnostic
reason, optional account/project IDs, request correlation ID, and investigation
status. Lookup, timestamp, category, and error-code indexes are present.
Account/project IDs are nullable and currently left unset; request bodies,
passwords, cookies, invitation tokens, GitHub credentials, authorization
headers, and customer file contents are never stored.

Validation and normal authorization/invitation rejections are `expected`.
Unexpected Worker/upstream failures and 5xx responses are `unexpected`.
Rate-limited authentication/invitation operations are elevated to category
`SEC` with high severity to flag repeated attempts. File and GitHub rate-limit
events use their operation category. Every failure write is limited to 50
incidents per UTC hour. Important successful operations
(authentication, invitation changes, project creation, file writes, GitHub
sync/configuration, and checkout) use a separate 100-events-per-hour budget.
Write-budget rows are bounded to one row per hour and event kind. Incidents are
retained for 90 days; successful-operation events for 30 days. Retention
cleanup runs hourly through the existing scheduled Worker.

If incident insertion fails or the incident budget is exhausted, the original
HTTP status and error fields are returned with `incidentRecorded: false`.
Structured fallback logs contain only the reference and safe registry/route
metadata, never raw request data or exception messages. Persistence failures
never turn an API success into an error. Success events contain only the
operation, component, category, status, timestamp, and request ID.

No diagnostic query API is implemented. Any future diagnostic endpoint must
authorize privileged staff roles on the server and return 404 for unauthorized
callers; ordinary customer sessions must never retrieve another customer's
incident records.

## Dashboard integration

- Read the `reference` from each backend error response and preserve it in
  support reports; do not generate or substitute a frontend reference.
- Accept both `BBB-{CATEGORY}-{12_HEX}` and historical `BBB-XXXXXXXX`
  references. Frontend-only errors use a visibly separate `CLIENT-{12_HEX}`
  reference, labeled as frontend-only and not automatically recorded in D1.
- Treat `incidentRecorded: false` as an explicit indication that D1 lookup is
  not guaranteed. The user can still provide the reference for Worker-log
  correlation.
- Continue mapping by the existing `error` identifier and `code`; do not infer
  HTTP status from the BBB numeric code.
- Use the `message` field as the safe customer-facing text. Do not expose
  internal diagnostic reasons.
- Copyable reports contain only allowlisted diagnostic metadata and the safe
  customer-facing message. They are not transmitted automatically and must
  never include tokens, cookies, passwords, or private content.
- Keep current credentials, Origin, cookie, invitation, and rate-limit
  behavior unchanged.

## Validation

The backend suite covers secure reference generation and uniqueness, stable
code/category mappings, D1 retrieval, expected and unexpected classification,
sensitive-data redaction, concurrent failures, persistence failure fallback,
and important successful-operation events.

Latest validation: `npm test -- --run` passed all 110 tests across five test
files; `npm run build` passed TypeScript checking and Wrangler's production
dry-run build. `git diff --check` reported no whitespace errors.
